# M3 — Repository, processor, notifier, API, maintenance, demo target

**Built:** DynamoDB single-table repository; processor (SQS batch → state machine → one transaction → SNS); notifier (Web Push with VAPID + PagerDuty Events v2); the API (Powertools Function URL resolver, JWT auth, origin check, all routes in HANDOVER §9); daily maintenance (TLS expiry + summary push); the demo target. 370+ tests, ~99% core coverage, all AWS calls against moto.

**Why this design:**
- **Idempotency (ADR 0011):** the raw-check `Put … if not exists` inside one `TransactWriteItems` is the idempotency key; optimistic locking on `version` handles two regions racing.
- **Partial batch failures:** one poison message goes back to SQS (and later the DLQ) without failing the other nine.
- **Dead-man's switch:** healthchecks.io is pinged only after a clean batch.
- **Front door:** CloudFront adds a secret `X-Beacon-Origin` header; the API rejects anything without it (constant-time compare), so the public Function URL is useless on its own.
- **Auth:** argon2id hash in SSM, HS256 JWT with the algorithm pinned (no `alg: none`), 5 failures → 15-minute lock.
- **SSRF everywhere:** product URLs are checked on create/update; push endpoints must be real push services (the notifier POSTs to them).
- **Email via SNS `MessageStructure=json`:** the notifier gets JSON, email gets readable text, subjects are ASCII-only (SNS rule).

**Interview questions**
1. *How do you make an SQS consumer idempotent?* Use a natural idempotency key (product, region, runAt) and write it conditionally in the same transaction as the side effects.
2. *What's optimistic locking?* Read a version, write "only if version unchanged", retry on conflict. No locks held, safe for concurrent Lambdas.
3. *Why report partial batch failures?* Without it, one bad message makes Lambda retry all ten, and successful work is redone.
4. *How do you stop someone calling your Lambda Function URL directly?* A secret header only CloudFront knows, checked in constant time.
5. *Why at-most-once alert publishing?* Publishing after commit means a crash can lose an alert, but never duplicates a page; the dead-man's switch and alarms cover a processor that is failing.
