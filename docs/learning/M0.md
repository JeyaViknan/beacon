# M0 — Scaffold

**Built:** repo layout from HANDOVER §17, `pyproject.toml` (ruff + pytest + coverage), pinned per-Lambda requirements, `Makefile`, and a Vite + React 18 + TypeScript (strict) + Tailwind v4 skeleton with Vitest and ESLint.

**Why this shape:**
- One shared package (`services/beacon_core`) holds all business logic as pure functions; each Lambda folder is a thin handler. Logic is testable without AWS, and every zip vendors the same core.
- Requirements are pinned exactly (`==`) per function, so a Lambda zip built today and next week is byte-for-byte the same dependency set. Each function only ships what it imports (the notifier carries `pywebpush`, the API carries `argon2`).
- Ruff enforces type hints (`ANN`), no `print` (`T20`), no blind `except` (`BLE`), bandit security rules (`S`) and timezone-aware datetimes (`DTZ`), so the code-style rules are checked by a machine, not by memory.
- Coverage gate (85%) is measured only on `beacon_core`, where the logic lives.

**Interview questions**
1. *Why pin dependencies exactly for Lambda?* Reproducible builds: the same commit always produces the same artifact; upgrades are explicit, reviewable commits.
2. *Why keep handlers thin?* Pure functions can be table-tested in milliseconds without mocks; the handler is just I/O glue, which integration tests cover with moto.
3. *What does `make lint test` protect against?* Style drift, missing type hints, unsafe patterns (bandit), and regressions in business logic — the same commands run in CI.
4. *Why a Makefile when CI exists?* One entry point for humans and CI; CI calls the same targets, so "works on my machine" and "works in CI" mean the same thing.
