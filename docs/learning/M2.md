# M2 — Checks, SSRF guard, probe Lambda

**Built:** `ssrf.py` (URL + DNS + IP checks, IP pinning), `checks.py` (one HTTP check with status ranges, keyword in the first 1 MB, timeouts, max 3 redirects, short error texts), `snapshot.py` (monitor snapshot + 30 s cache), and the probe handler that sends exactly one SQS message per run.

**Why this design:**
- **SSRF (ADR 0010):** resolve first, block if *any* address is private, then connect to the checked IP with the hostname in `Host`/SNI. That defeats DNS rebinding, and TLS is still verified for the real name. In Lambda the juicy target is the runtime API on `127.0.0.1:9001`.
- **One message per run, even when empty:** the processor pings healthchecks.io per batch, so an empty message still proves scheduler → probe → SQS → processor works.
- **Budget overrun is "no data", not "down":** if the 45 s budget runs out, unfinished checks are skipped, because the probe being slow says nothing about the product.
- **Snapshot cache (30 s):** a warm probe container does one DynamoDB read per 30 s regardless of product count.
- **Concurrency:** asyncio + semaphore(20); one slow site cannot stall the others.

**Interview questions**
1. *What is SSRF and why does an uptime monitor care?* Server-side request forgery: making the server fetch internal URLs. A monitor fetches user-supplied URLs by design, so it must refuse internal addresses.
2. *What is DNS rebinding and how do you stop it?* The name resolves to a public IP at check time and a private one at connect time. Pin the checked IP and connect to it directly.
3. *How do you keep TLS verification when connecting by IP?* Send the hostname as SNI and verify the certificate against it (httpx `sni_hostname` extension).
4. *Why disable connection reuse?* Pooled connections are keyed by IP; reusing a TLS session made for host A to talk to host B on the same IP would give wrong results.
5. *What happens if a probe run takes too long?* Unfinished checks are cancelled and skipped (logged), never reported as failures.
