# M7 — Operating Beacon: alarms, runbooks, paging, RCAs

**Built:** runbooks for all 9 alarms plus the dead-man's switch and a product-DOWN playbook (`docs/runbooks/`), the RCA template and the first real RCA (`docs/incidents/`), alarm descriptions that link straight to their runbook, `make test-alarm` / `make demo-*`, skippable `make secrets` prompts, and the healthchecks.io + PagerDuty setup guide.

**Why this design:**
- **Every alarm is actionable:** it has a runbook with the first question to ask, exact commands, and when to escalate. An alarm without a runbook is just noise at 3 a.m.
- **ALARM and OK both notify,** so PagerDuty incidents open *and resolve* automatically (CloudWatch integration).
- **Independent paths (ADR 0009):** product alerts go through Beacon's notifier, but Beacon's own alarms reach PagerDuty via SNS directly, and the dead-man's switch lives outside AWS. A broken Beacon can still page.
- **Blameless RCAs** with 5 Whys end in *guardrails*, not people. The real 2026-10-23 incident produced two fixes: Lambda code via S3 (ADR 0013), and each probe's schedule now waits for the processor's SQS trigger (`consumer_ready`), so a producer never starts before its consumer. A module-level `depends_on` was tried first, but it made every plan show the probe's IAM as changing, so the link is scoped to the schedule only.
- **Testable alerting:** `make test-alarm` forces a real ALARM through the real path; it returns to OK on the next evaluation.

**Interview questions**
1. *What makes a good alert?* It's actionable, urgent, and has an owner and a runbook. Everything else is a dashboard or a ticket.
2. *Who watches the watcher?* A heartbeat to healthchecks.io after every clean batch; silence for 5 minutes pages, even if AWS is down.
3. *Walk me through an incident you handled.* The 2026-10-23 queue backlog: detection by `results-queue-age` in about 7 minutes, root cause a half-applied deploy, two guardrails added. See the RCA.
4. *Why page on symptoms (queue age) as well as causes (errors)?* Symptoms catch failures you didn't predict: the trigger simply didn't exist, so there were no errors at all.
5. *How do you test your alerting?* Force an alarm state with `set-alarm-state`, run game-day drills (break the demo target, deploy a failing processor), then write the RCA.
