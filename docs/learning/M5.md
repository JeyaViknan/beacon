# M5 — The PWA

**Built:** React 18 + TypeScript (strict) app: login, home (status pill, counts, filters, product cards with a 24h strip), product detail (incident banner + Acknowledge, uptime/latency/p95, error budget, 24h response-time chart, 30-day bars, incidents, recent checks, Test now, pause/resume, edit, delete), add/edit form, incidents feed, settings (push, channels, demo break/fix, version, logout). The service worker precaches the shell, serves `/api` network-first, and shows pushes. 65 Vitest tests.

**Why this design:**
- **PWA over native (ADR 0001):** Web Push works on iOS 16.4+ once the app is on the Home Screen. Deploys are an S3 sync, with no App Store.
- **Permission from a tap:** `Notification.requestPermission()` is the first call in the button handler. iOS refuses prompts that aren't user-initiated.
- **Every push shows a notification:** iOS revokes push for apps that receive silent pushes. `tag = productId`, so RECOVERED replaces DOWN.
- **TanStack Query:** caching, a 30 s auto-refresh, refetch on focus, and no retries on 4xx. A 401 clears the token and sends you to login.
- **Offline:** the shell is precached, and the last good API response comes from the `beacon-api` cache, with a banner saying so.
- **Accessibility:** status is always icon + text, 44 px touch targets, safe-area insets, reduced-motion respected, and form hints linked via `aria-describedby`.
- **Code-split detail page:** the chart library loads only when you open a product.

**Interview questions**
1. *How does Web Push work?* The browser subscribes with our VAPID public key and gets an endpoint on Apple's/Google's push service. The server signs a JWT with the VAPID private key and POSTs an encrypted payload to that endpoint. The service worker's `push` handler shows it.
2. *Why a service worker?* It receives pushes when the app is closed, caches the shell for instant/offline loads, and handles notification taps.
3. *Network-first vs cache-first?* API data must be fresh, so network-first with a cache fallback. Hashed JS/CSS never change, so they are precached.
4. *How is the token protected?* It's short-lived-ish (30 days), HS256 with a pinned algorithm, and only sent to same-origin `/api`. A strict CSP (`default-src 'self'`) limits XSS damage.
5. *How do you test UI logic?* Pure functions (sorting, time, schema, install tip) as unit tests, and pages with Testing Library against a stubbed `fetch`.
