# M6 — CI/CD with GitHub Actions and OIDC

**Built:** `ci.yml` (Python, web, Terraform, and Lambda-package jobs in parallel) and `deploy.yml` (CI → approval → OIDC → plan/apply → publish web → smoke test), plus `scripts/smoke_test.sh` and `scripts/smoke_lambda_imports.sh`.

**Why this design (ADR 0014):**
- **No long-lived AWS keys:** GitHub mints a short-lived OIDC token for the job, and AWS STS swaps it for role credentials only if `aud = sts.amazonaws.com` and `sub = repo:JeyaViknan@157094732/beacon@1431377621:environment:production`. That's GitHub's immutable subject: owner and repo are pinned by ID, so a recreated repo with the same name can't impersonate this one.
- **Human gate:** the `production` environment requires Jeya's approval, and the role only trusts that environment, so even a malicious workflow on another branch can't get AWS credentials.
- **Same checks everywhere:** deploy calls the CI workflow, and CI calls the same `make` targets used locally.
- **Smoke test proves the new version is live:** `/api/health` must return the deployed commit's short SHA, not just "ok".
- **Real runtime check:** handler imports run inside AWS's own Lambda arm64 image, so a wrong-architecture wheel fails in CI, not in production.
- **Supply chain:** actions are pinned to SHAs, and workflow inputs reach the shell only via `env:`.

**Interview questions**
1. *How does GitHub Actions authenticate to AWS without secrets?* OIDC federation: the job's signed JWT is exchanged via `AssumeRoleWithWebIdentity`, and the role trust policy checks audience and subject (repo + environment).
2. *How do you stop a PR from a fork deploying?* Deploys run only on `main` pushes in the protected `production` environment, which needs approval, and the AWS role trusts only that environment's subject.
3. *Why pin actions to a SHA?* Tags are mutable. A compromised action repo could move `v4` to malicious code; a SHA is immutable.
4. *What does your smoke test check?* The API is healthy and running exactly the commit just deployed, and the app shell is served.
5. *Your first deploy failed with "Not authorized to perform sts:AssumeRoleWithWebIdentity". How did you debug it?* CloudTrail logs the refused call with the subject GitHub presented. It was the immutable `owner@id/repo@id` format, not the name-based one in my trust policy, so I pinned the trust to the ID-based subject: a one-line fix that's also stricter.
6. *How do you roll back?* `git revert` the bad commit, then the pipeline redeploys the previous state after approval. Terraform state and deterministic zips make it reproducible.
