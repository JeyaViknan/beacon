# M1 — beacon_core: models, state machine, uptime maths

**Built:** pydantic v2 models (camelCase on the wire, snake_case in Python), the incident state machine, uptime / p95 / error-budget maths, and UTC/IST time helpers. 141 tests, 100% coverage of `beacon_core`.

**Why this design:**
- `evaluate()` is a **pure function**: product + one region result + time in, `Evaluation` out (new state, rollup delta, incident opened/resolved, alerts). No clock, no I/O, no random IDs (the incident ULID is passed in), so every rule is a table row in a test.
- **Idempotency starts here:** a result not newer than the region's last result is a `duplicate` and changes nothing; an older minute is `late` and never steps counters.
- **Quorum + consecutive thresholds** (ADR 0005) prevent paging on a single blip or a single bad region.
- **Uptime = upMin / totalMin**, counted per product-minute (not per region), paused minutes excluded. Daily buckets use IST dates because a "day" is Jeya's day.
- **Error budget:** `(1 − SLO) × monitored minutes − down minutes`. At 99.5% over 30 days that is 216 minutes.

**Interview questions**
1. *How do you avoid false alarms?* Two consecutive failing minutes (configurable) and, with multiple regions, a majority quorum of fresh regions.
2. *What happens if SQS delivers the same message twice?* The state machine sees the region's result is not newer → `duplicate` → nothing written. M3 adds a DynamoDB conditional write as the second guard.
3. *What is an error budget?* The downtime the SLO allows: 99.5% of 43,200 min = 216 min/month. Remaining budget tells you whether you can afford risky changes.
4. *Why p95 and not average latency?* Averages hide the tail; p95 shows what 1 in 20 users experiences.
5. *Why pure functions?* Deterministic, fast, exhaustive tests; the Lambda handler is just I/O around them.
